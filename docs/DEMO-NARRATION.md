# متن گویندگی ویدیوی دمو (حدود ۵ دقیقه)

پیش‌نویس متن فارسی برای ضبط، هم‌راستا با سناریوهای [README](../README.md#۷-سناریوهای-دمو) و
[docs/03 §4](03-ui-demo-readme.md#demo-script). جمله‌ها کوتاه و محاوره‌ای‌اند تا راحت خوانده شوند؛ هر جا لازم بود
عوضشان کنید.

**قبل از ضبط:** `npm run chaos -- none --deploy` (یک نسخه‌ی سالمِ ثبت‌شده برای برگشت)، پوشه‌ی `~/my-shop` آماده،
مرورگر روی ۱۲۵٪، پایش خودکار برنامه‌ی دمو روشن. اگر رابط کاربری با Docker اجرا شده، دستورهای `npm run chaos` را با
`docker exec liara-agent …` بزنید (مثلاً `docker exec liara-agent npm run chaos -- leak --deploy --app my-shop`).

## ۰:۰۰ – ۰:۳۵ · معرفی

> **تصویر:** صفحه‌ی خوش‌آمد با دو دکمه.

«سلام. من برنامه‌نویسم و می‌خوام سایتم روی لیارا بالا بیاد، ولی دواپس بلد نیستم.
این «همکار فنی لیارا» است: یک دستیار هوشمند که با API رسمی لیارا کار می‌کند. پروژه را منتشر می‌کند، سرویس را زیر
نظر دارد، وقتی مشکلی پیش بیاید علتش را با شاهد پیدا می‌کند، با اجازه‌ی من درستش می‌کند و بعد بررسی می‌کند که
واقعاً درست شده باشد.»

## ۰:۳۵ – ۲:۰۰ · سناریوی ۱: اولین انتشار

> **تصویر:** نوشتن «این پروژه رو منتشر کن: ~/my-shop».

«فقط مسیر پروژه را می‌دهم.»

> **تصویر:** خط زمانی «تحلیل پروژه» و «پیشنهاد پلن»، بعد کارت پلن.

«پروژه را خودش تحلیل کرد: Node.js، پورت ۳۰۰۰، و یک متغیر محیطی لازم دارد. پلن را با دلیل و هزینه‌ی ماهانه
پیشنهاد داد و چک کرد موجودی حسابم کافی است. اسم سرویس را هم خودش از اسم پوشه انتخاب کرد.»

> **تصویر:** نوشتن `PAYMENT_API_KEY=demo` → کارت تأیید.

«مقدار کلید را خودم می‌دهم؛ هیچ مقدار محرمانه‌ای را حدس نمی‌زند. حالا قبل از هر تغییری می‌گوید دقیقاً چه کاری
می‌کند و چقدر هزینه دارد. تأیید می‌کنم.»

> **تصویر:** مراحل انتشار زنده جلو می‌رود → آدرس سایت و نوار سبز → باز کردن سایت.

«ساخت سرویس، متغیرها، بسته‌بندی، ارسال کد، ساخت نسخه و بررسی سلامت. سایت بالاست، و پایش خودکارش هم روشن شد.»

> **تصویر:** «دامنه‌ی myshop.ir رو وصل کن» → تأیید → کارت DNS و اعلان محدودیت ایرنیک.

«برای دامنه، رکوردی که باید در ایرنیک بسازم و مراحلش را دقیق نشان می‌دهد. صادقانه هم می‌گوید که خودش به پنل
ایرنیک دسترسی ندارد، ولی هر دقیقه بررسی می‌کند و وقتی وصل شد خبرم می‌کند.»

## ۲:۰۰ – ۳:۵۰ · سناریوی ۲: حادثه

> **پیش از این صحنه (خارج از قاب):** `npm run chaos -- leak --deploy` و حدود ۹۰ ثانیه صبر.
> **تصویر:** نوشتن «سایتم کند شده و گاهی ۵۰۰ می‌ده».

«سایتم کند شده. فقط همین را می‌گویم.»

> **تصویر:** خط زمانی «بررسی و عیب‌یابی»، بعد کارت تشخیص؛ باز کردن شواهد علت اول.

«رویدادها، لاگ‌ها، مصرف منابع و پاسخ واقعی سایت را یک‌جا جمع کرد. علت اول: کمبود رم. شاهدش هم این‌جاست:
رویداد OOMKilled، رم نزدیک سقف پلن، و خط خطای heap out of memory در لاگ. چون مشکل درست بعد از آخرین انتشار
شروع شده، برگشت به نسخه‌ی قبلی را پیشنهاد می‌دهد، نه فقط یک ری‌استارت موقت.»

> **تصویر:** کارت تأیید برگشت → «تأیید و اجرا» → مراحل انتشار → نوار سبز.

«تأیید می‌کنم. برگشت انجام شد و بعدش دوباره بررسی کرد: سایت ۲۰۰ جواب می‌دهد و از بعد از اقدام هیچ کمبود رمی
دیده نشده. فقط وقتی این بررسی موفق باشد می‌گوید «حل شد».»

## ۳:۵۰ – ۴:۳۰ · سناریوی ۳: هشدار خودکار و محدودیت‌ها

> **پیش از این صحنه:** `npm run chaos -- crash --deploy` و یکی دو دقیقه صبر.
> **تصویر:** بنر قرمز «کرش یا کمبود رم در …» → «بررسی کن».

«این بار من چیزی نپرسیدم؛ پایشگر خودش متوجه کرش شد و هشدار داد. تشخیص: کرش پشت‌سرهم، با همان خط کدی که خطا
داده. اصلاح کد کاری است که فقط من می‌توانم انجام بدهم، و این را صریح می‌گوید؛ تا آن موقع برگشت به نسخه‌ی سالم را
پیشنهاد می‌دهد.»

> **تصویر:** «لاگ‌های دسترسی HTTP رو نشون بده» → اعلان محدودیت.

«و اگر چیزی بخواهم که API لیارا ندارد، وانمود نمی‌کند؛ می‌گوید ممکن نیست و راه جایگزین را پیشنهاد می‌دهد.»

## ۴:۳۰ – ۵:۰۰ · MCP و جمع‌بندی

«همین ابزارها از طریق MCP داخل Claude Desktop و Cursor هم هست، با همان قواعد ایمنی.
سه چیز این دستیار را قابل اعتماد می‌کند: سطح ریسک هر کار در کد تعیین می‌شود نه در پرامپت، بعد از هر اقدام نتیجه
بررسی می‌شود، و محدودیت‌ها همیشه صریح گفته می‌شوند. ممنون.»
